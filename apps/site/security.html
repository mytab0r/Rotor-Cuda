Security advisories

Published vulnerabilities and threat classes that affect wallet keys and addresses. Each entry explains the impact in plain language, names primary sources and says whether a local check exists.

How to read this page

This page is documentation, not a protection service. It cannot stop a theft, recover funds or prove that a key is safe. It lists only publicly documented issues, and every entry cites a primary source. An entry ships only after a reviewer checks its facts and records the review date.

A local check reads only the address you enter in this browser. It never sends an address to this site or to a third party. A bounded local scan covers only the range you choose, so a no-match result is not a safety guarantee.

Milk Sad: weak entropy in libbitcoin-explorer bx seed

CRITICALCVE-2023-39910VulnerabilityReviewed 2026-11-22

libbitcoin-explorer 3.x generated the seed material behind its bx seed command with a Mersenne Twister PRNG seeded by 32 bits of system time. Instead of a 256-bit key space, a wallet made from that output has about 2^32 possible seeds. Anyone who guesses the generation time can reproduce the same wallet.

What it means for you

A Bitcoin wallet whose seed came from an affected bx seed version can be regenerated by someone else and its funds can be swept. A key created with a proper operating-system CSPRNG is not affected by this bug, and an idle vulnerable key cannot be protected by watching it.

Affected

  • libbitcoin-explorer 3.x (bx seed)
  • wallets or services that generated keys from bx seed output

What to do

  1. If a wallet was created with libbitcoin-explorer 3.x or a service that used its bx seed output, create a new wallet with a reputable CSPRNG and a fresh seed phrase.
  2. Move the funds to the new wallet as soon as possible, starting with the highest-value addresses.
  3. Do not reuse the old seed phrase after moving the funds; treat the old key as public.
  4. Use the official Milk Sad research and its checker for the exact affected versions and test vectors.
  5. Use the local seed-range scan on this site only for an address you control; it reproduces keys in this tab and sends nothing.

Local check on this site

Reproduces bx-seed wallets from a 32-bit MT19937 seed in this tab and compares only the public Bitcoin address the user supplies. The scan makes no network request.

Open the local checker

A no-match result covers only the seed range entered. The weak set spans 2^32 seeds, so a bounded scan cannot prove a key is safe.

Primary sources

  • Milk Sad research (primary)
  • NVD: CVE-2023-39910 (primary)

Android SecureRandom weakness in wallets created in 2013

HIGHCVE-2013-7372VulnerabilityReviewed 2026-11-22

Android builds before 4.4 (API 19) could return predictable output from the platform SecureRandom implementation. Bitcoin wallet apps that generated keys on an affected device could therefore produce keys that another device could also produce. The failure is in the platform random-number generator, not in secp256k1 or in a correctly seeded wallet.

What it means for you

A wallet created on an affected Android device in 2013 may share its key with someone else. The risk depends on the device, the Android version and the wallet app; an address alone does not reveal how its key was generated, so this site cannot run a local check for it.

Affected

  • Android apps using the platform SecureRandom before Android 4.4 (API 19)
  • Bitcoin wallet apps that generated keys on those devices in 2013

What to do

  1. If a wallet was created on an Android device before Android 4.4 in 2013, create a new wallet on a device with a current, patched operating system.
  2. Move the funds to the new wallet; do not keep relying on the old key.
  3. Update the device or wallet app if it is still in use, and read the original bitcoin.org alert for the affected wallet versions.
  4. Treat this entry as history for old wallets; a wallet created today with a current OS and a proper CSPRNG is not affected by this 2013 platform bug.

No local check

This site does not ship a local check for this entry. An address alone cannot show which random-number generator or device produced its key, so a check here would be a guess. Use the primary sources and the wallet's own creation history.

Primary sources

  • NVD: CVE-2013-7372 (primary)
  • bitcoin.org alert: Android SecureRandom bug (primary)

Threat classes

These are scam techniques, not software bugs: there is no affected version and no patch. They are kept separate so a version update is never presented as a fix for them.

Address poisoning and dusting

HIGHThreat classReviewed 2026-11-22

An attacker sends a tiny amount of a token or coin from an address chosen to look like one the victim already uses: the same first and last characters, often the same length. The fake address then appears in the victim's transaction history. When the victim later copies an address from history instead of checking it, the transfer goes to the attacker.

What it means for you

Funds sent to the lookalike address are lost to the attacker. This is a social-engineering trick, not a break of the wallet software or of the key: no patch fixes it, and a wallet cannot prove that an address is the one the user intended.

What to do

  1. Verify the whole address before sending, not only the first and last four characters.
  2. Use an address book or a saved contact for repeat payments; never copy a counterparty from transaction history.
  3. Treat unexpected tiny incoming transfers as untrusted data and ignore them.
  4. Check the destination on a block explorer and confirm it matches the address you intended to pay.
  5. Do not interact with tokens or approvals that arrive from addresses you do not recognise.

Primary sources

  • Etherscan Information Center: address poisoning attacks (primary)

Why this page does not list vulnerable keys

A searchable directory of every weak key and its balance is a target list, not a safety tool. It helps someone take funds from wallets they do not own. The owner of an affected wallet already has the public research and the official checker; publishing the whole enumeration adds no protection for that owner.

How entries are reviewed

An advisory stays in draft until a human or agent reviewer checks the summary, the affected tools and versions, and the actions against the primary sources. The reviewer records their identifier and the review date in the data file. A superseded entry stays visible with its history instead of disappearing.
