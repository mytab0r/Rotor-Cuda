## Finding 1: multi-thread checkpoint resume silently skips unscanned keys
- Gate: review
- Risk: blocker
- Evidence: src/engine.rs:110-135 (baseline = saved.count; start = start + count, then
  split_range re-splits the remaining range) and src/engine.rs:862 (count = baseline + scanned,
  the global sum over all workers). With N > 1 threads every worker scans its own chunk from
  its low end, so the scanned set is N separate per-chunk prefixes, never one contiguous
  prefix. Shifting the global start by the total count skips the unscanned tail of chunk 0
  and all unscanned low parts of chunks 1..N-1.
  Concrete failure: range [1,100], -t 2, chunk = 50. Workers scan [1,50) and [50,100); each
  has scanned 10 keys at crash time (count = 20). Resume scans [21,100]. Keys 11-20 and 51-60
  were already scanned; keys 21-50 of chunk 0 were never scanned and never will be. Silent
  false negative.
  C++ reference: Rotor.cpp:640-644 shifts EACH thread chunk start by value777/nbit2
  (nbit2 = thread count, Main.cpp:646), i.e. count/threads per chunk, correct under uniform
  progress. The Rust port replaced this with a global shift; design.md cites Rotor.cpp:213-255
  but the port does not implement the per-thread model.
- Alternative: shift each chunk start by count/threads (C++ model), or write per-chunk
  offsets in the checkpoint - accepted, must be implemented. Current code is rejected.
- Status: open

  Skew analysis (the requested special attention): saved chunk count c_i is bounded by the
  chunk length L_i (worker counter only accumulates its own batches), so the shifted window
  [lo_i + c_i, min(hi_i + c_i, end)] always satisfies (W_i = scanned [lo_i, lo_i + c_i))
  union (R_i) containing [lo_i, hi_i]: the gap between chunk i stop (hi_i + c_i) and chunk
  i+1 resume (lo_{i+1} + c_{i+1}) lies inside chunk i+1 already-scanned region, so it is a
  rescan/skip of ALREADY scanned keys only - no key is skipped. A finished chunk (c_i >= L_i)
  yields shift_chunk None and is skipped safely; clipping at end is correct for the last
  chunk. Differing per-worker counts therefore cannot lose keys. Union over chunks of
  [lo_i, hi_i] = the full range.
  Old-format fallback (engine.rs:928): count/chunk_count per chunk reproduces the C++ model
  (Rotor.cpp:641-644, value777/nbit2) exactly; its skew approximation is C++ parity by design
