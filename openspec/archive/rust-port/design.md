# Design: Rust-порт CPU-части

## Решения

### D1. Один Cargo-пакет в корне репозитория

`Cargo.toml` + `src/` в корне; C++-дерево остаётся в `Rotor-Cuda/` как референс и
источник CUDA-кернелов. Пакет `rotor` (lib + bin). Без workspace: GPU-часть, когда
появится, станет отдельным крейтом в том же workspace.

Причина: `cargo build --release` из корня; не плодим слои.

### D2. Своя арифметика поля вместо k256

Причина: k256/`primeorder` не отдают координаты проективной точки, поэтому пакетная
нормализация (одна инверсия на 1024–2048 точек) недоступна — без неё каждая точка
требует отдельной инверсии, это ~10× просадка горячего цикла.

Реализация:
- `Fe` — элемент GF(p), p = 2^256 − 2^32 − 977; представление 4×u64 в Монтгомери-форме
  (R = 2^256), умножение CIOS на `u128`.
- `Scalar` — элемент GF(n) (порядок группы), та же схема, отдельные константы.
- `Point` — якобиевы координаты; mixed addition (Z2 = 1), doubling, `batch_to_affine`
  через `IntGroup`-алгоритм (n−1 mul, 1 invert, n−1 mul).
- `compress`/`decompress` — sqrt = a^((p+1)/4), т.к. p ≡ 3 (mod 4).

Векторы: известные pubkey/hash160, WIF (см. тесты), плюс BSGS-фикстуры из
`bsgs/bsgs_selftest.cpp`.

### D3. Хэши — RustCrypto

`sha2`, `ripemd`, `sha3` (Keccak-256). Один проход `hash160 = ripemd160(sha256(pub))`.
SSE-батчи из C++ не портируются: выигрыш <2×, сложность высокая; при необходимости
добавим `sha2`-asm feature или ручной 4-lane позже.

### D4. CLI — ручной парсер

Флаги C++ имеют пересекающуюся семантику (`-n` = чекпоинт-минуты в range-режиме и
бит-диапазон в random-режиме), clap это усложняет. Ручной разбор ~120 строк даёт
точные сообщения и коды возврата. `--help` — дословно из `Main.cpp:39-79`.

### D5. GPU — граница

`-g` принимается, но без `--features gpu` печатает `GPU code not compiled` и выходит
с ненулевым кодом (как C++ без `WITHGPU`). CUDA-кернелы не трогаем до отдельного change.

### D6. Многопоточность

`std::thread::scope`, по числу `available_parallelism()`; каждый поток получает
непересекающийся поддиапазон (как `Thread NNN : start -> end` в C++). Общий счётчик
найденного — `AtomicU64`; запись в `Found.txt` — под `Mutex` с flush.

### D7. Форматы

- Вход `.bin`: сырые записи по 20 (hash160/keccak) или 32 (xpoint) байта, без
  заголовка (`Puzzles_1_37_ETH.bin`: 740 = 37×20). Порт сортирует записи сам.
- `Found.txt`: `PubAddress` / `Priv (WIF)` (BTC) / `Priv (HEX)` / `PubK (HEX)`,
  разделитель 86 `=` (`Rotor.cpp:352-367`).
- Чекпоинты: `Rotor-Cuda_Continue.bat` (7 строк) и `Rotor-Cuda_START.bat` (4 строки),
  см. ниже. `Rotor-Cuda.user` — файл настроек Visual Studio, к чекпоинтам отношения
  не имеет.

## Форматы (по факту исходников)

### Чекпоинт `-n` (Rotor.cpp:1599-1616, 213-255; CmdParse.cpp:86-103)

Файл `Rotor-Cuda_Continue.bat`, 7 строк:
```
:loop 
<командная строка с именем экзешника>
goto :loop 
created: <ctime>
<count>
To continue correctly, DO NOT change the parameters in this file! 
If you no longer need the continuation, DELETE this file! 
```
При старте, если `Rotor-Cuda_Continue.bat` отсутствует/пуст, пишется
`Rotor-Cuda_START.bat`: `:loop ` / `<exe> <args> ` / `goto :loop ` / пустая.
Возобновление: `count` прибавляется к стартовому ключу и к счётчику.
Запись — при `rKey == 0` и `next > 0`, период `next * 55` секунд (так в коде:
`minuty++` раз в секунду, порог `next*55`, `Rotor.cpp:1597-1618`).
Точный resume: после 7 стандартных строк пишутся `threads: <n>` и
`chunks: <c0>,<c1>,...` — кумулятивные счётчики воркеров (C++ читает только 5 строк).
Окно чанка i сдвигается на `ci` с обрезкой концом диапазона; без расширения или
при другом числе потоков — fallback `count / threads` на каждый чанк.

### Раскладка диапазона (Rotor.cpp:1455-1511)

`diff = (end-start)/(cpu+gpu)`, поток i получает `[start+i*diff, start+(i+1)*diff)`.
CPU-группа 2048 точек: центр `(key+1024)·G`, ±iG, пакетная инверсия, hash160.

### `-i` .bin (Rotor.cpp:80-102, 3292-3323)

Сырые записи 20 (hash160/ETH keccak) или 32 (xpoint) байта, без заголовка.
C++ ищет `memcmp`-бинарным поиском и **требует предварительной сортировки** файла;
реализация поиска содержит дефекты (нулевая запись и часть хвоста недостижимы).
Порт сортирует записи копии при загрузке и делает корректный бинарный поиск, поэтому
несортированный файл тоже работает. Это осознанное отклонение: баг C++ не
воспроизводим без потери корректности.

### CPU-BSGS (BsgsCpu.cpp)

`m = isqrt(span+1)+1`; baby: `jG`, ключ — FNV-1a/64 по 32-байтному big-endian X в
`HashMap<u64,u32>`; giant: `R=target-kStart·G`, `R-i·S`; при совпадении fold —
точная перепроверка точки. C++ берёт span только из младших 64 бит (`:79-82`) —
порт считает полный 256-битный span (отклонение-исправление, фиксируется в README).
Файл `Found.txt`-вывод BSGS: `<target pubkey> <key hex>\n` (append).

### `-l/--list`

На Windows C++ печатает CUDA-инфо; в Rust-сборке без GPU — `GPU code not compiled`.

### Имя бинаря

Cargo-бин `rotor`; упаковка релиза может копировать его в `Rotor-Cuda.exe` для
совместимости со старыми `.bat`. Внутри генерируемых `.bat` — фактическое имя.

## Осознанные отклонения от C++

1. `-g` без GPU-feature — явная ошибка с кодом ≠ 0. C++ в этой ветке печатает
   `GPU code not compiled` и продолжает как no-op (`Rotor.cpp:1380-1383`).
2. Бинарный поиск по `.bin` корректный; C++-версия теряет запись 0 и часть хвоста
   (`Rotor.cpp:3292-3323`). Вход по-прежнему должен быть отсортирован.
3. CPU-BSGS считает span полностью (256 бит) и при `m > u32::MAX` падает громко;
   C++ берёт младшие 64 бита span и молча считает не то (`BsgsCpu.cpp:79-82`).
4. BinaryFuse не портируется в первой итерации (результат не меняется).
5. `--update`/`--check-update` — явная ошибка «не поддерживается», а не WinHTTP.
6. Баннер при resume показывает фактический (сдвинутый) старт; C++ печатает
   исходный `rangeStart`, хотя сканирует со сдвигом (`Rotor.cpp:280`).
7. BSGS-манифест возвращается в `BsgsResult`, но на диск не пишется — как и в C++
   (`BsgsCpu.h` описывает его как identity для будущего resume, файла нет).
8. `-t 0` завершается ошибкой «no CPU threads requested» (C++ запускает 0 воркеров).

## Bloom

C++ использует libbloom-совместимые параметры: `bits = entries·(−ln ε)/ln²2`,
`hashes = ceil(ln 2 · bits/entries)`, двойное хеширование по **MurmurHash2 (32-bit)**
(`Bloom.cpp:256-301`). Файлового формата Bloom нет (`save`/`load` — заглушки),
поэтому порт свободен в выборе внутреннего представления, но сохраняет эти параметры
и MurmurHash2 для предсказуемого false-positive rate.
