# Review 2026-11-15: rust-selfupdate (post-implementation)

VERDICT: PASS

## Findings

1. No HTTP status check after WinHttpReceiveResponse
   - Gate: review | Severity: minor
   - Evidence: src/selfupdate.rs:479 (https_get returns body without reading the status code).
   - Scenario: asset missing/renamed or a CDN 5xx -> github.com returns an HTML error body with
     404/5xx; it is written to .new and only rejected later as "sha256 mismatch" (misleading),
     wasting a full multi-MB download. Safe: the hash gate still blocks a bad swap. The API path
     is covered: a 403 rate-limit JSON has "message" and parse_release_json_for surfaces it
     (selfupdate.rs:246-250, test parse_surfaces_github_api_error_message).
   - Alternative: check WinHttpQueryHeaders status == 200 per request - rejected here as
     cosmetic robustness, hash gate keeps correctness.

2. Relaunch spawn failure is swallowed
   - Gate: review | Severity: minor
   - Evidence: src/selfupdate.rs:166 `let _ = command.spawn();` then exit(0).
   - Scenario: spawn fails (e.g. AV policy) -> binary is updated but nothing restarts and the
     user just sees the process exit; .old lingers until the next manual launch (cleanup_old is
     best-effort). Mirrors C++ CreateProcessA handling; data-safe.

3. .new litter on two error paths
   - Gate: review | Severity: minor
   - Evidence: src/selfupdate.rs:133 (fs::write failure can leave a partial .new);
     src/selfupdate.rs:161/306 (install_new_exe failure after rollback leaves .new).
   - Scenario: disk-full during write -> partial rotor.exe.new stays; harmless (next update
     overwrites it), but cleanup on every error path would be tidier. The sha-download, hash-read
     and mismatch paths DO clean up (lines 139, 152, 157).

4. asset_url name/url pairing is nearest-after, not per-object
   - Gate: review | Severity: minor
   - Evidence: src/selfupdate.rs:209-231: a matched "name" pairs with the first
     browser_download_url anywhere later in the document, not necessarily inside the same asset
     object.
   - Scenario: only if an asset lacked browser_download_url (never happens in real GitHub
     payloads) could a name steal a later asset URL. Wrong-asset cross-match of the actual
     suffixes is impossible: "Rotor-Cuda.exe", "rotor-gpu.exe", "rotor.exe.sha256" all fail
     ends_with("rotor.exe") (verified char-by-char).

5. Design/code drift on VERSION default
   - Gate: review | Severity: minor
   - Evidence: design.md D5 says default "2.0.0-dev"; code (selfupdate.rs:19-22) uses "dev" ->
     0.0.0, so a local dev build always reports an update available. Intended per code comment;
     design.md should be corrected on archive.

6. Restart loop check - confirmed safe
   - Gate: review | Severity: info
   - Evidence: main.rs:89-94 passes argv (incl. --update) to the relaunched exe; the release
     binary is stamped ROTOR_VERSION=<tag> by rust-release.yml:20-22, and
     version_cmp("vX","vX") == Equal -> main.rs:84 prints "already up to date" and returns. No
     loop. Residual: a manually uploaded asset built without ROTOR_VERSION (dev=0.0.0) would loop
     on --update until the unauthenticated API rate limit makes check_latest fail with exit 1 -
     bounded, C++ had the same property.

## Fine
- WinHTTP handles are RAII-guarded (selfupdate.rs:332-342); closed exactly once on every path
  incl. early returns via ?; no double close, no leak.
- wide() NUL-terminates UTF-16 (selfupdate.rs:345-347); u32::MAX length for AddRequestHeaders
  matches the C++ (DWORD)-1; windows-sys 0.59.0 locked (Cargo.lock:178-180) and signatures/flags
  (INTERNET_DEFAULT_HTTPS_PORT, WINHTTP_FLAG_SECURE, ADDREQ_FLAG_ADD) match.
- User-Agent + Accept set (selfupdate.rs:473-476) - GitHub API requirement met.
- Default WinHTTP redirect policy follows the github.com -> objects.githubusercontent.com 302 for
  browser_download_url and disallows https->http downgrades; no custom policy needed.
- read_all loop: QueryDataAvailable/ReadData, truncate to got, terminate on available==0 - short
  reads cannot corrupt; a truncated download is caught by the hash.
- Hash computed on .new before any swap (selfupdate.rs:149 before 161); empty-hash guard (156);
  short/failed exe download never reaches install.
- install_new_exe: stale .old non-NotFound error aborts BEFORE renaming the live exe (298-302);
  rollback restores old binary on second-rename failure (306-313); cleanup ignores only missing
  files per contract.
- version_cmp reproduces the C++ selftest cases incl. missing-component-zero and no-digit=0;
  u64 saturating arithmetic is strictly stronger than C++ long overflow.
- Non-Windows: check_latest/apply_update return Err(NOT_SUPPORTED); main.rs:102-106 exits 2 with
  a message; no windows-only imports leak (asset_suffixes/winhttp are cfg(windows)).
- Workflow: "$hash  rotor.exe" is lowercase two-space sha256sum format, pwsh 7 writes utf8NoBOM
  (CRLF tolerated by split_whitespace); asset names rotor.exe/rotor.exe.sha256 match
  asset_suffixes(); tag guard startsWith(refs/tags/) prevents workflow_dispatch from publishing.
- Tests are non-vacuous: parse tests assert exact URLs (CPU asset picked, C++ asset ignored,
  GPU suffixes, missing-asset errors, rate-limit message); swap tests assert file contents
  through swap, rollback and double-cleanup.

## Known accepted gap
- The full network + swap path was never executed end-to-end (tasks.md item 5 admits: no
  rotor.exe asset in any release yet, IP rate-limited). First real release should verify
  --update on a throwaway install before advertising it.

## Verdict rationale
No critical or major defects: the dangerous paths (bad download, hash mismatch, swap failure,
stale .old) all fail loud or roll back, and the restart cannot loop. Findings 1-3 are robustness
polish; 4-5 are theoretical/doc. Approve; recommend follow-up issue for the status-code check.
